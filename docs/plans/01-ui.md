# UI plan

Status: draft, living document. Follows [00-overview.md](00-overview.md); decisions and their rationale are logged in [../decisions.md](../decisions.md) (D20 to D22 for this plan).

The data, domain and state layers are done. This plan covers the UI built on top of them: what it looks like, how it behaves, the order we build it in, and what we are deliberately not doing.

## 1. Principles

- **A complete app comes first, polish second.** Every step below leaves the app working. The animations come after the control panel, so that if time runs short, the resilience demonstration is finished and the flourishes are what is missing.
- **No logic in widgets.** Widgets read state and dispatch intents. Rules (what a move does, when a card reveals) live in domain or state code and are unit tested.
- **Every state is designed.** Loading, empty, error (with retry) and "incomplete analysis" are shown explicitly, never as a blank space.
- **Accessible by default.** Contrast in both themes, keyboard reachable controls, semantics labels, and reduced-motion support.

## 2. Layout

One main screen rather than many routes. Breakpoints are starting points, to be tuned by eye.

| Width | Layout |
|---|---|
| Wide (about 1000 px and up) | Search panel on the left. Team slots and coverage matrix on the right. |
| Medium | Single column: team slots, then coverage matrix. Search opens in a bottom sheet. |
| Narrow (phone) | As medium, with the six slots reflowed (for example 2 x 3). |

- **Search on narrow and medium screens** is a modal bottom sheet, nearly full height, with the field focused. Tapping an empty slot or an "Add Pokémon" button opens it. Choosing a result closes the sheet and starts the throw animation, so the sheet does not hide it. It is the same search widget as the wide panel, hosted differently.
- **Detail** is the flip dialog (section 6).
- **Compare** is a second view, reached from a button.
- **Control panel** is a drawer or dialog, so it never gets in the way but can be opened live.

## 3. Theme

- **Modes:** light, dark, and "system" (follows the browser's preference, which Flutter reads on the web). A three-way segmented control chooses between them.
- **Persistence:** the choice is stored through the existing `KeyValueStore` (on the web that is `localStorage`), under one key, as `system`, `light` or `dark`. An unknown or missing value means `system`.
- **No flash at start-up.** The saved choice is read before the first frame, so someone who chose light in a dark browser never sees dark first. This is the one place start-up reads storage outside a notifier, because the theme is needed for the very first frame, unlike the team, which can arrive a moment later (D17).
- **Type colours:** one colour per type, kept in the `app` layer (the domain has no colours). Text on a badge is white or black, whichever contrasts better with the background, with a test that every type reaches the WCAG AA contrast of 4.5. **Built in step 3**, with the first widget that shows a type badge, rather than in step 1 where nothing would use them yet.
- **Accent:** indigo, from a single seed colour shared by the light and dark themes. Not red, because red already means "error" in Material and would also be mistaken for the fire type.
- **Where it lives:** `features/theme` holds the repository, notifier and three-button picker (they deal in Flutter's `ThemeMode`, so they cannot be in the plain-Dart `data` layer). `main` waits for the saved choice before `runApp`, using a container it creates itself.
- Material is the base (D8), with a custom colour scheme, typography and component themes. Component themes are added as the widgets that need them are built.

## 4. The team: six fixed slots

The UI always shows six slots, filled or empty. This needs a model change (D20): the team becomes a sparse list.

- `Team` holds six slots; each is an id or empty.
- `add(id)` fills the first empty slot. `addAt(i, id)` fills slot `i` if it is empty (and never overwrites). `removeAt(i)` empties slot `i`; nothing else moves.
- `move(from, to)` exchanges two slots (see section 5).
- Saved as `{"ids":[25,null,6,null,null,null]}`. Loading stays defensive: anything that is not a whole number becomes an empty slot, and extra entries past six are dropped. Old compact saves such as `[25,6]` load as the first two slots.
- The analysis skips empty slots. `missingCount` still counts only members that are loading or failed.

What this gives the UI: stable slot identity, Hero tags that are the slot index, a throw animation that always has a target on screen, no layout jump when the team changes size, and slots that only reflow at breakpoints.

## 5. Reordering (D21)

- Drag a card onto another slot and the two **swap**. Dropping on an empty slot moves the card there.
- Built with Flutter's `Draggable` and `DragTarget`. The drag only starts after the pointer has moved a small distance, which is the minimum-distance rule; the exact threshold is checked in the SDK source when built.
- While dragging: the origin slot shows a faded placeholder, and the slot under the pointer highlights. On drop the two cards cross-fade into place.
- **Not doing:** shuffling the other cards out of the way as you drag. It is insert-and-shift behaviour, which conflicts with fixed slots, and it is hard in a layout that changes between a row, a grid and a stack. Listed as a known limitation.
- **Without a mouse:** dragging is not reachable by keyboard or screen reader, so each card exposes semantics actions ("move earlier", "move later"), and the detail dialog has the same two buttons. On touch screens a plain drag can fight with page scrolling; if so, switch to long-press then drag.
- **Animations must not fire on a move.** The throw plays when a Pokémon is added or the saved team loads, never because "this slot became filled", or dragging into an empty slot would throw a ball. The state layer therefore records which slots have just arrived (added, or loaded at start-up) and the widgets do not infer it by comparing before and after.

## 6. Animation and the detail dialog

All custom-painted with `CustomPaint`; no image assets.

- **Throw-in:** a ball, drawn in code, starts large and off towards the bottom-left of its slot, as if thrown over the viewer's shoulder, then shrinks along an arc into the slot. It is followed by a "flash" (a radial gradient that scales up and fades), which fades to reveal the card.
- **Reveal rule:** the card reveals only when **both** a minimum duration has passed **and** the Pokémon's data has loaded. A slow load delays the reveal. A failed load opens to an error card with a retry button, never a stuck ball. The rule is a small pure function with its own tests.
- **Saved team on start-up:** each filled slot throws, about 100 ms apart, and each reveals under the same rule.
- **Animates inside each slot** rather than in a full-screen overlay, which is simpler and survives scrolling and resizing. Revisit only if it looks wrong.
- **Flip-to-dialog:** selecting a card grows it into a dialog while rotating around the vertical axis, using a `Hero` transition with a custom shuttle builder that swaps the front face for the back face at the halfway point. Hero tags are the slot index (the same Pokémon can fill several slots). The dialog holds the detail: types, base stats, the radar chart, and "move earlier / later". This is the fiddliest piece. If it proves stubborn, the fallback is a grow-and-fade dialog and nothing else changes.
- **Reduced motion:** when the system asks for less animation (`MediaQuery.disableAnimations`), the throw and flip are skipped: cards appear immediately and the dialog fades.

## 7. Coverage matrix

- One row per attacking type (18), showing which members are weak, resistant or immune, with counts. Exposed types are highlighted and described in plain language.
- **Incomplete analysis is always said out loud.** When `missingCount` is not zero, a message says so and that the picture may be incomplete, because a team that looks safe may only be missing a member.
- `Unavailable` (the type chart failed) shows the typed reason with a retry button.

## 8. Build order

Each step ends with tests and a working app.

1. **Theme:** light, dark, system; persistence; no first-frame flash; the toggle. **Done** (type colours moved to step 3).
2. **Sparse team model (D20):** `Team`, `TeamRepository`, `TeamNotifier`, analysis provider, with `move`. Unit tests, including old saved formats. **Done.**
3. **Search and static team slots:** type colours and badges, search state (index provider and query), the wide panel and the bottom sheet, six slots with add and remove, each slot's loading and error states, sprites with placeholder and error handling.
4. **Reordering:** drag to swap, with the semantics actions.
5. **Coverage matrix:** including the incomplete and unavailable states.
6. **Control panel:** the levers; move the fault settings provider into `features/control_panel`; the cache "clear" lever; decide the timeout policy (the current worst case is about 31 seconds: retry a timeout at most once, or shorten the timeout).
7. **Throw-in animation** and reduced-motion support.
8. **Flip detail dialog**, with the radar chart and move buttons.
9. **Compare view**, reusing the radar chart. First candidate to shrink or cut if time runs short.
10. **README**, with the manual test plan and known limitations; delete `scratch_home.dart`.

## 9. Testing approach

- **Domain and state:** plain unit tests (team rules, `move`, saved-format handling, the reveal rule, theme mode storage).
- **Widgets:** widget tests with the fake API client and in-memory store. Animations are tested by pumping through their durations, which is deterministic. The reduced-motion path is tested.
- **Manual test plan** (README): throttling, offline mode, clear storage, narrow widths, keyboard and screen-reader pass, light/dark/system, a reload with a saved team, and a check that persistence survives a real browser reload (so far tested only against in-memory storage).

## 10. Known limitations to record

- Reordering swaps; it does not shuffle other cards along.
- Dragging has no direct keyboard route; the move buttons and semantics actions stand in for it.
- A blocked-storage browser loses the team and the theme choice on reload without telling the user (D17).

## 11. Open questions

- The exact shape of "which slots have just arrived" in the state layer (section 5). Decided when the animation is built; the requirement is fixed.
- Breakpoint values and the slot reflow on phones, settled by eye in step 3.
